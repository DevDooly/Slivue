# Slivue Google Play 제출 준비·심사 점검표

## 1. 상태와 책임 경계

- 기준일: **2026-10-31**. 준비 대상은 첫 무료·무광고 Google Play판이다.
- 사용자가 Play 앱을 아직 등록하지 않았다고 확인했다. 이번에 **Play판 `com.devdooly.slivue`**, 기존 직접 배포판 `com.devdooly.notificationedge`로 분리하기로 선택했다.
- 공개 개발자 표시 이름·개인정보 문의 이메일은 **미정**이다. 공개 정책 URL·최종 시행일도 확정 전이다.
- 앱 생성, Play App Signing 약관 동의·앱 서명키 등록, AAB 업로드, 국가·연령·등급 선택, 테스트 참여자 등록, 심사 제출·게시를 이 문서가 대신 실행하거나 승인하지 않는다.
- 아래의 **P0는 해결·검증·소유자 확인 전 제출하지 않는 항목**이다. 빌드 성공, 코드 검토, 정적 검사, 에뮬레이터 검증, 실제 Play 설치 검증은 서로 다른 증거다.

관련 자료: [구현·실제 검증 보고서](GOOGLE_PLAY_PREPARATION_REPORT.md), [전체 계획](GOOGLE_PLAY_LAUNCH_PLAN.md), [개인정보 준비서](GOOGLE_PLAY_PRIVACY_AND_DATA_SAFETY.md), [서명 전략](GOOGLE_PLAY_SIGNING_AND_MONETIZATION.md), [한·영 등록정보 안내](GOOGLE_PLAY_LISTING_GUIDE.md).

## 4. 개인정보처리방침 확정 게이트

준비 파일은 [한국어 HTML](privacy/ko.html), [영어 HTML](privacy/en.html)이며 앱 내부에도 같은 초안을 둔다. 앱 내부에서 읽을 수 있다는 사실만으로 공개 URL 요건이 충족되지는 않는다.

- [ ] **P0** 공개 운영 주체 이름과 실제 관리하는 문의 이메일 확정. 추측한 주소·예시 주소로 대체하지 않기.
- [ ] **P0** 공개 정책 URL과 최종 시행일 확정. 현재 파일의 준비본 경고를 검증 없이 숨기지 않기.
- [ ] **P0** 대상 패키지·알림 정보·백그라운드 처리·빠른 답장·저장·삭제·외부 전달·권한 선택 설명을 최종 앱과 대조.
- [ ] **P0** 최종 정책이 로그인·지역 제한 없이 읽히는 HTTPS 웹페이지인지 확인. PDF·다운로드 링크·GitHub의 HTML 소스 보기로 대체하지 않기.
- [ ] 앱 내부 전문과 공개 정책 내용·버전이 일치하고, 온라인 정책은 외부 브라우저에서 올바른 주소로 열리는지 확인.
- [ ] 호스팅 제공자 및 문의 수신 서비스에서 접속·메일 정보를 처리하는 범위를 운영 방침에 반영. 알림 자체 처리와 구분.
- [ ] Google Play의 정책 URL·스토어 지원 정보·실제 운영 주체가 일치하는지 확인.
- [ ] 운영 주체·배포 국가별 법률 적합성을 실제 상황에 맞게 검토. 코드 작성만으로 법률 검토를 완료 처리하지 않기.

공식 요구는 공개 웹 접근성, 앱별 데이터 처리의 구체성, 앱 내부 안내와 스토어 링크를 포함한다. [User Data 정책](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en), [심사 준비 안내](https://support.google.com/googleplay/android-developer/answer/9859455?hl=en)

## 6. Data safety 잠정 답안과 증거

**제출할 최종 답안이 아니다.** Google의 “수집”은 일반적으로 앱/SDK가 정보를 기기 밖으로 보내는 경우를 포함하고, 기기 안에서만 처리하는 정보와 구분한다. 기기 안 다른 앱 전달도 공유 검토 대상이며, 사용자 요청에 따른 명확한 동작 등의 예외는 조건을 확인해야 한다. [Data safety 공식 정의](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en)

| 질문·정보 | Play판 설계에 따른 잠정 답 | 확정하기 전 필요한 증거 |
| --- | --- | --- |
| 알림 본문·제목·발신자·앱 정보 | 로컬 처리만 확인되면 기기 밖 수집 없음 후보 | 최종 AAB·SDK·동의 전후·백그라운드·로그·전송 검사 |
| 빠른 답장 | 원래 앱에 사용자 지시로 전달. 무조건 “아무 공유 없음”이라고 단정하지 않음 | 실제 답장 UI·고지와 사용자 요청 예외 적용 조건 대조 |
| 발견 앱·차단어·환경 설정 | 내부 저장, Play 백업 제외 설계 | cloud/D2D 최종 규칙·복원 결과·외부 전송 부재 |
| 사용자 폰트 | 시스템 파일 선택·내부 복사, Google Fonts 제공자 제외 설계 | 최종 의존성·DEX·동작·폰트 삭제 확인 |
| IP·기기 식별자·오류·사용량 | 자체 네트워크·광고·분석 SDK 제외 설계 | `INTERNET` 권한 부재만으로 완료 처리하지 않고 전이 SDK·다른 앱 전달·실제 트래픽 검토 |
| 외부 브라우저/스토어 열기 | 사용자가 선택해 외부 앱으로 이동 | 정보가 담긴 URL/추가값을 붙이지 않는지, 외부 서비스 정책 범위 구분 |
| 개인정보 지원 문의 | 연락처·수신 경로 미정 | 최종 문의 서비스와 운영자 처리·보유·삭제 안내 확정 |
| 광고 포함 여부 | 첫 Play판에 광고 기능·SDK가 없을 때 “아니요” 후보 | 최종 런타임 의존성·화면·모든 활성 버전 확인 |
| 계정 생성·계정 삭제 | Slivue 계정 생성이 없으면 계정 삭제 웹 경로가 필요한 계정 기능과 구분 | 최종 로그인·회원가입 기능 부재 확인 |

확정 시 보관할 증거:

1. 제출 AAB의 SHA-256, 패키지·버전·서명/업로드 키 공개 지문, 생성한 APK 검사 결과.
2. merged manifest, DEX/의존성 목록: 설치 권한·업데이터·Google Fonts 제공자·원문 진단 내보내기·광고/분석 SDK 제외 여부.
3. 합성 알림을 이용한 최초 실행·동의 전후·거부·중지·철회·재개·폰트 가져오기·외부 링크·재부팅별 트래픽/로그 검사. 사용자의 실제 메시지는 시험 자료로 쓰지 않기.
4. 백업·복원·기기 이전 결과 및 삭제 결과. `allowBackup=false`만으로 모든 제조사의 결과를 단정하지 않기.
5. 위 자료와 정책·스토어 문구·Data safety의 교차 검수 기록과 소유자 최종 확인.

모든 활성 Play 버전·지역을 포함해 신고한다. 향후 광고·분석·계정·동기화 기능을 추가하면 기능을 배포하기 전에 다시 검토하고 신고를 갱신한다. 보호 기능이나 인증서 검증을 끄고 실측하지 않는다.

## 7. FGS·알림 접근 심사 설명 초안

### 기능과 유형

- 핵심 기능: 사용자가 선택한 화면 가장자리 핸들과 새 알림의 엣지 라이팅을 다른 앱 사용 중에도 제공한다.
- 선언 후보: `FOREGROUND_SERVICE_SPECIAL_USE`와 `specialUse`. 미디어 재생·데이터 동기화 유형을 실제 기능과 다르게 선택하지 않는다.
- 지속 동작이 필요한 이유: 핸들이 사용자가 설정한 위치에서 즉시 제스처를 받고, 사용자가 켠 라이팅이 수신 알림에 반응해야 한다. 중단·지연 시 핸들이 사라지거나 알림 강조가 늦어져 사용자가 요청한 기능을 수행하지 못한다.
- 사용자 통제: 설정에서 시작·전체 중지·재개, 실행 상태 알림과 중지 동작 제공. 사용자가 중지하거나 권한을 철회한 상태를 부팅·외부 명령으로 우회하지 않는다.
- 데이터: 리스너의 알림 접근은 별도 앱 내부 동의와 시스템 권한이 모두 있어야 하며, 핸들·라이팅의 오버레이 권한과 구분한다.

`specialUse`의 적절성은 Play 검토 대상이며 승인 보장이 아니다. manifest에 기능을 구체적으로 설명하고, Console에는 해당 기능·지연/중단 영향·사용자가 시작하는 과정을 보여 주는 영상과 필요한 자료를 제출한다. [FGS 신고 공식 안내](https://support.google.com/googleplay/android-developer/answer/13392821?hl=en), [specialUse 유형](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use)

### 시연 영상 촬영 순서

1. 제출할 Play 빌드의 버전·기기/Android 버전을 보여 준다. 실제 개인 메시지나 계정 정보는 노출하지 않는다.
2. 설정·개인정보처리방침·고지 내용을 보여 주고, **나중에**를 눌러도 접근이 시작되지 않는 것을 시연한다.
3. 다시 고지를 열어 동의한 뒤 시스템 알림 접근·오버레이 권한을 직접 허용하고 앱으로 복귀한다. 알림 보내기 권한은 별도 항목으로 보여 준다.
4. 핸들·라이팅을 사용자가 켜는 경로와 실행 상태 알림을 보여 준다.
5. 합성 알림이 뜨면 패널을 열어 제목·본문·대화·앱별/키워드 필터를 보여 준다. 빠른 답장은 `RemoteInput` 지원 시험 알림으로 재현하고 해당 원래 앱으로 전달된다는 점을 설명한다.
6. 설정 또는 서비스 알림에서 **전체 중지**를 눌러 핸들·라이팅·처리가 멈추고 이력이 비워지는 것을 보여 준다.
7. 사용자가 재개한 뒤 OS 알림 접근을 철회하여 중단되는 것을 확인한다. 재개하려면 다시 조건을 만족해야 함을 보여 준다.
8. 일반 뒤로가기·키보드 닫기·큰 글씨 등 핵심 접근성 동작을 짧게 확인한다.

심사 접근 안내에는 로그인·OTP가 필요하지 않음을 적되, 합성 알림을 생성하는 정확한 방법·필요한 권한·지원 기기 조건은 최종 구현을 기준으로 제공한다. 아직 없는 샘플 모드나 도구가 있는 것처럼 신고하지 않는다. 영상 URL은 심사자가 로그인 없이 볼 수 있는지 확인한다.

## 8. Play Console에서 소유자가 마무리할 항목

- [ ] 계정 유형·생성일·국가·개발자 검증·연락처를 실제 Console에서 확인한다. 필요한 개인정보를 Git/Slack 문서에 올리지 않는다.
- [ ] 새 패키지 `com.devdooly.slivue` 앱을 만든다. 업로드 키와 Play 앱 서명키를 구분해 선택하고 공개 인증서 지문만 기록한다.
- [ ] 공개 정책·한영 등록정보·지원 이메일·실제 스크린샷·기능 그래픽·아이콘 규격·권리를 확인한다.
- [ ] 앱 콘텐츠의 광고, 앱 접근, 대상 연령, IARC 등급, Data safety, FGS/요청된 권한 정보를 실제 기능대로 입력한다. 연령·등급을 추측해 고정하지 않는다.
- [ ] 업로드 사전 검사를 통과한 AAB를 내부 테스트에 올리고 Play가 서명한 설치물로 신규 설치와 다음 Play 후보 업데이트를 확인한다. 내부 앱 공유의 재서명은 실제 앱 서명 검증과 구분한다.
- [ ] Pre-launch report·충돌·ANR·16KB·기기별 필수 흐름을 확인하고 해결한다.
- [ ] 해당하는 신규 개인 계정이면 실제 테스터 최소 12명의 연속 14일 비공개 테스트와 피드백 반영 후 프로덕션 액세스를 신청한다. 에뮬레이터나 내부 테스트만으로 대체하지 않는다. 조건 충족이 자동 승인을 뜻하지 않는다. [공식 테스트 안내](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)
- [ ] 모든 P0 해소 후 제출·게시 내용을 최종 확인하고 Play 심사를 진행한다. 승인·게시일은 보장하지 않는다.

## 9. 후속 기록란

### 로컬 후보와 최종 준비 명령

```powershell
# 서명·운영 정보 없이 만들 수 있는 기술 검증 후보. 제출용이 아니다.
.\gradlew.bat testPlayDebugUnitTest lintPlayRelease bundlePlayRelease
node scripts/verify-play-artifact.mjs app/build/outputs/bundle/playRelease/app-play-release.aab

# 운영 정보·정책·별도 업로드 키가 준비됐는지 확인한다. 현재 상태에서는 실패가 정상이다.
.\gradlew.bat verifyPlaySubmissionReady

# 위 조건과 실제 모든 AAB 항목의 업로드 서명 검사를 통과한 경우에만 별도 후보를 만든다.
.\gradlew.bat preparePlaySubmission
```

최종 준비 전에는 공개 메타데이터 `PLAY_DEVELOPER_NAME`, `PLAY_SUPPORT_EMAIL`, `PLAY_PRIVACY_POLICY_URL`과 독립적인 `PLAY_UPLOAD_STORE_FILE`, `PLAY_UPLOAD_STORE_PASSWORD`, `PLAY_UPLOAD_KEY_ALIAS`, `PLAY_UPLOAD_KEY_PASSWORD`를 로컬 비밀 환경에 설정한다. `PLAY_POLICY_APPROVED=true`는 운영자 검토를 실제 완료한 뒤에만 설정한다. 비밀번호나 개인키를 채팅·문서·원격 저장소에 쓰지 않는다.

기술 검증용 미서명 후보를 만들 때는 `PLAY_UPLOAD_*` 네 항목을 모두 비운다. 한 항목이라도 설정했는데 완비되지 않으면 Play release 산출물 생성을 즉시 거절한다. 네 항목이 완비되면 `bundlePlayRelease`·`assemblePlayRelease`뿐 아니라 실제 `package`·`sign` 태스크도 최종 준비 게이트를 먼저 통과해야 하므로, 원래 출력 경로에서 서명 AAB를 만드는 방식으로 초안 방침 검사를 건너뛸 수 없다. 이 조건은 축소 release 변형에도 적용한다. 디버그 빌드는 별도 debug 서명을 사용하며 항상 준비 빌드 안내를 표시한다. 안내 플래그 자체는 Console 승인 증거가 아니다.

정책 승인 플래그 하나만으로 통과하지 않는다. 앱/공개 전문은 바이트가 같아야 하며 두 언어 모두 본문에 실제 운영 이름·이메일·공개 URL이 반영되어야 한다. 초안·미정 문구가 없어야 하고, `<meta name="slivue-policy-status" content="final">` 및 동일한 실제 시행일 `<meta name="slivue-policy-effective-date" content="YYYY-MM-DD">`가 필요하다. 지금의 준비본에서 표시만 바꾸지 말고 최종 처리·통신·권한·삭제 동작을 다시 검토한다.

`app/build/play-submission/latest-attempt.json`에서 **이번 시도** 결과를 확인한다. 과거 후보가 있어도 이번 시도가 `not_ready`라면 제출에 사용하지 않는다. 성공 시에는 UTC 시각·SHA 기반 폴더의 AAB와 `verification.json`을 함께 보관한다. 이때도 로컬 준비 확인일 뿐 Play 앱 서명 등록·계정 적격성·공개 URL 실제 접근성·심사 승인 증거는 아니다.

Node의 `--require-upload-signature`는 서명 파일 존재와 정책·구조 검사이며, 실제 암호학적 서명과 지정 인증서 일치는 Gradle 준비 단계의 `JarFile`이 모든 본문을 읽어 검증한다. 기존 legacy/direct 인증서를 업로드 키로 재사용하면 거절한다. 최종 Play 앱 서명키는 이 업로드 키와 별도로 Console에서 선택한다.

한·영 기능 그래픽은 [한국어 PNG](google-play/graphics/feature-ko.png)·[영어 PNG](google-play/graphics/feature-en.png)와 같은 폴더의 SVG 원본을 준비했다. 1024×500·불투명 RGB이며, 실제 스크린샷과 원본 자산의 권리 검토는 별도다.
