# Slivue 서명·공개 소스·수익화 전략

## 2026-10-31 결정 — Play는 별도 신규 패키지

사용자가 Play판만 `com.devdooly.slivue`, 직접 배포판은 기존 `com.devdooly.notificationedge` 유지로 결정했다. 따라서 아래의 기존 계보를 Play로 이관하는 검토는 **동일 패키지를 선택했을 때의 과거 대안**으로 보존한다. 이번 Play판에는 적용하지 않는다. 두 앱은 별도 설치이며 자동 설정·권한 이전이 없다.

Play 전용 업로드 키와 새 앱 서명은 별도 역할이다. 기존 노출 legacy 키나 direct 인증서를 새 업로드 키로 재사용하지 않는다. `preparePlaySubmission`은 운영 정보·정책 확정·실제 업로드 서명을 검증한 로컬 후보 생성일 뿐, Console 앱 서명 등록·약관 동의·업로드를 수행하지 않는다. 첫 Play 앱 서명키 선택과 실제 Play 설치물의 업데이트 검증은 소유자 작업으로 남아 있다. [제출 점검표](GOOGLE_PLAY_SUBMISSION_CHECKLIST.md)

## 1. 권고 결론

기준일 2026-09-05, 소스 v1.3.19(`4837ea2`). **첫 목표는 무광고 Play 출시다. GitHub 공개를 유지하고, 서명 호환성과 Play 전용 배포 경로부터 확정한다.** 광고 SDK·결제 기능·저장소 비공개 전환은 이번 계획 작성에서 실행하지 않았다.

## 2. 첫 Play 등록에서 서명이 중요한 이유

현재 직접 배포 APK는 `com.devdooly.notificationedge` 패키지를 사용한다. v1.3.16부터 API 28 이상은 회전된 새 인증서, API 26~27은 기존 설치 호환용 인증서를 사용한다. 이전 키가 공개 이력에 남아 있는 상태는 [서명 실행서](SIGNING_KEY_ROTATION_RUNBOOK.md)에 기록되어 있다.

지금까지 CI가 확인한 것은 **GitHub APK → 다음 GitHub APK**의 업데이트다. **GitHub APK → Google Play가 서명한 APK**의 성공은 아직 확인하지 않았다.

| 구분 | 역할 | 주의점 |
| --- | --- | --- |
| Play 업로드 키 | 개발자가 AAB에 서명하여 업로드 주체를 확인 | 재설정 가능. 이를 바꿔도 기존 앱 서명키 노출이 해결되지는 않음 |
| Play 앱 서명키 | Play가 사용자에게 전달하는 APK의 서명 | 설치·업데이트 호환성의 기준. 처음 선택할 때 신중해야 함 |
| 기존 직접 배포 계보 | 과거·새 인증서의 관계와 OS별 서명 사용 | Play 등록 지원과 실제 배포된 인증서가 일치하는지 시험 |

새 Play 앱에 개발자의 기존 서명키를 제공하는 경로는 있다. 그러나 이 앱은 이미 외부에서 회전 계보로 배포했으므로 일반적인 새 키 업로드 사례와 같다고 가정하지 않는다. Android 문서에 기존 계보가 있는 APK의 v3 지원 조건이 별도로 있고, Play의 서명 업그레이드 옵션도 변화하므로 **실제 Console 옵션/필요 시 지원 답변을 확인하는 P0 결정 게이트**를 둔다. 불가능하다고 단정하거나, 새 키만 올리면 모든 기존 설치본이 유지된다고 약속하지 않는다. [Android 앱 서명](https://developer.android.com/studio/publish/app-signing), [Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756?hl=en)

### P0 결정 절차

1. 계정 소유자가 신규 앱·패키지 등록 가능 여부와 앱 무결성 설정을 확인한다.
2. 기존/새 공개 인증서 지문, 회전 최소 API, 이전 배포 버전 목록을 정리한다. 키 원문·비밀번호는 문서나 Slack에 넣지 않는다.
3. 외부 배포된 현재 계보의 최초 Play 등록 가능 여부와 기기별 실제 앱 서명 구성을 확인한다. 기본 Google 생성 키를 무심코 확정하지 않는다.
4. **별도 안전한 업로드 키**를 준비하고, 앱 서명키 이전이 필요하면 Console이 지정한 PEPK 절차와 소유자 승인 아래 수행한다. 공개 이력에 노출된 기존 개인 서명키를 안전한 키로 재분류하지 않는다. 공개 인증서·지문과 개인키는 구분한다.
5. AAB를 내부 테스트 트랙에 올린 뒤 Play가 생성한 APK의 인증서·계보를 검사한다.
6. 아래 호환성 표를 실제 설치로 검증한 뒤 최초 프로덕션 서명 결정을 확정한다.

| 출발 설치본 | 도착 설치본 | 확인 사항 |
| --- | --- | --- |
| 미설치 | Play 후보 | 신규 설치·권한 온보딩 |
| 기존 키만 사용한 v1.3.15 | Play 후보 | 설치 가능 여부, UID·설정·권한 유지 |
| 회전 계보의 v1.3.19 | Play 후보 | 동일 항목, OS별 서명 선택 |
| Play 후보 | 다음 Play 후보 | 정상 업데이트·롤아웃 운영 |
| Play 후보 | 직접 배포판 | 계속 지원할 경우에만 별도 검증. 자동으로 약속하지 않음 |

시험 대상은 최소 API 26·27·28·32·33·35·36과 One UI 실기기를 권고한다. 이는 이 프로젝트의 서명 경계 확인용이지 모든 앱에 대한 Play 공통 의무 기기 목록은 아니다.

**주의: Internal App Sharing은 별도 테스트 인증서로 재서명된다.** 기존 설치본과의 호환성 시험에는 내부 테스트 트랙이나 App Bundle Explorer에서 얻은 실제 앱 서명 APK를 사용한다. 내부 앱 공유에서 설치됐다는 사실만으로 Play 업데이트 가능성을 판정하지 않는다. [내부 앱 공유의 서명](https://support.google.com/googleplay/android-developer/answer/9844679?hl=en)

### 동일 패키지가 어려울 때의 대안

| 대안 | 장점 | 결정 전에 확인할 비용 |
| --- | --- | --- |
| 기존 패키지·호환 서명 유지 | 기존 사용자의 설정·설치 연속성 가능 | Console 수용성, OS별 검증, legacy 지원 구간의 잔여 위험 |
| 지원 OS 범위 조정 | 노출키만 지원하는 구간의 부담 축소 가능 | 기존 기기 지원 종료·이전 안내. 이것만으로 전체 서명 문제가 해결되지는 않음 |
| 새 패키지·새 앱 서명 | 과거 노출키와 분리된 새 출발 | 별도 앱 설치·권한 재설정·데이터 이전·기존 사용자 안내 필요 |

새 패키지는 기존 개발 규칙을 변경하는 사용자 결정이 필요하다. 이번 문서는 이름을 임의로 정하거나 패키지를 바꾸지 않는다. 서명 문제 때문에 기존 앱을 먼저 삭제하도록 사용자에게 요구해서도 안 된다.

## 3. Play와 직접 배포의 운영 경계

- Play용: AAB, Play 업데이트 경로, 자체 APK 설치 권한/코드 제외.
- 직접 배포용: 유지한다면 기존 GitHub 업데이트의 보안 검증과 공개 자산 경로를 보존.
- 같은 패키지로 병행한다면 서명·versionCode·채널 전환 우선순위를 공통 대장으로 관리.
- Play 업로드 키·앱 서명키·직접 배포 키·CI 접근 권한을 구분하고 최소 권한·2단계 인증·복구 시험 적용.
- 공개 소스와 릴리스 서명 비밀은 철저히 분리. 공개 저장소에도 비밀 스캔·푸시 보호 유지.

새 Play 키를 선택하기 전 기존 사용자 유지 범위를 먼저 결정한다. Play와 직접 배포 양쪽에 새로운 키 정책을 동시에 강제 적용하는 작업은 별도 실행 계획과 시험이 필요하다.

## 4. 공개 소스를 유지해도 수익화할 수 있는가?

**가능하다. 공개 저장소를 닫는 것이 Play 출시나 광고 수익화의 전제는 아니다.** 현재 Apache-2.0는 조건 준수 하에 상업적 이용을 허용한다. 공식 배포판의 신뢰·업데이트·지원·브랜드·UX가 경쟁력이 될 수 있다. [Apache 공식 FAQ](https://www.apache.org/foundation/license-faq.html)

다만 공개를 유지하면 다른 사람이 적법하게 코드를 수정·재배포하거나 광고 없는 포크를 만들 수 있다. 이를 기술적 비밀로 막겠다는 수익 계획은 맞지 않는다. 차별화된 지원·디자인·운영 가치를 기준으로 판단한다.

이미 Apache로 배포된 코드의 적법한 이용 권리는 저장소를 private로 바꾸는 것만으로 회수되지 않는다. 향후 비공개 수정판을 운영하더라도 기존 및 제3자 라이선스·고지 의무는 남는다. 상표 사용은 코드 라이선스와 별도이며, 새 브랜드 정책을 만들더라도 과거 허락을 소급 취소하는 것으로 설명하지 않는다. 권리 해석과 기여자 소유권은 필요 시 전문가 검토를 받는다. [Apache-2.0 본문](https://www.apache.org/licenses/LICENSE-2.0)

### 지금 private 전환을 권하지 않는 실무적 이유

1. [현 업데이터](../app/src/main/java/com/devdooly/notificationedge/data/updater/AppUpdateManager.kt)는 인증 없는 `DevDooly/message_edge/releases/latest`와 공개 APK URL을 사용한다. private 전환 시 기존 설치 앱의 조회·다운로드가 중단될 것으로 판단된다. 이를 해결하려고 개인 액세스 토큰을 앱에 넣으면 안 된다. [GitHub Release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)
2. 기존 공개 포크·다운로드본·노출키는 회수되지 않는다. private 전환은 노출 비밀 복구 대책이 아니다.
3. 문서·개인정보처리방침을 같은 저장소의 Pages에 호스팅한다면 요금제·공개 접근 유지 조건도 확인해야 한다. [GitHub 공개 범위 변경](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)

향후 비공개가 필요한 기능이 생기면 **공개 배포/문서 주소 확보 → 기존 앱의 새 업데이트 경로 전환 → 설치 사용자 영향 확인 → 소스 비공개 결정** 순서로 별도 진행한다. 첫 출시 전에는 공개를 유지하는 것이 변경 범위가 작다.

## 5. 출시 전 권리·라이선스 체크리스트

- [ ] 런타임/전이 의존성의 라이선스와 필요한 NOTICE·저작권 고지를 산출
- [ ] 앱 내 오픈소스 고지와 배포 파일에 필요한 내용을 반영
- [ ] 외부 코드·AI 보조 코드·기여자의 출처와 권리 확인. Git 저자 수를 단독 저작권 증거로 쓰지 않기
- [ ] 현재 서체 Noto Sans KR·IBM Plex Sans KR·Nanum Gothic·Gowun Dodum과 제공자의 라이선스 확인. Google Fonts의 상업 사용 안내가 모든 사용자 업로드 폰트의 재배포를 허락하는 것은 아님
- [ ] 아이콘 원본·참조 이미지·생성 도구·수정 이력·상업 사용 조건 기록
- [ ] Slivue 유사 앱명·상표 충돌 조사, 타 메신저/삼성의 공식 제휴처럼 보이는 표현 제거
- [ ] 실제 개인 이름·프로필·메시지 대신 합성 데이터로 스토어 캡처
- [ ] 코드 라이선스·앱 상표·개별 자산 라이선스를 구분

현재 추적 파일에 사용자 폰트 바이너리가 없다는 사실만으로 모든 자산 권리가 정리된 것은 아니다. 실제 배포 산출물 기준으로 검수한다. [Google Fonts 안내](https://developers.google.com/fonts)

## 6. 출시 후 수익화 계획

### 단계 A — 무료·무광고로 출시

광고·분석·계정 SDK를 추가하지 않는다. 알림 접근에 대한 신뢰와 기본 기능, 권한 이탈·충돌·배터리 문제 해결이 우선이다. 별도 사용자 추적을 넣기 전에 Play Console의 집계 지표와 직접 받은 피드백을 활용한다.

### 단계 B — 운영 품질을 보고 도입 여부 판단

수익화 시작 기준은 다운로드 수 하나가 아니다. 다음은 **운영 권고**이며 Google의 광고 승인 기준이나 확정 매출 조건이 아니다.

- 일정 기간 핵심 기능과 권한 흐름이 안정적이고 반복되는 개인정보 불만이 없음.
- 유지율·활성 사용자·삭제 추세와 자발적 피드백에서 확인한 이탈 이유·지원 부담을 설명할 수 있음.
- 광고를 허용할 일반 앱 화면에 실제 방문이 있는지 확인됨.
- SDK·동의·처리방침·Data safety·광고 품질 검수 준비가 됨.
- 광고 때문에 핵심 알림 처리·앱 신뢰가 악화되면 즉시 중단할 수 있음.

Slivue의 주 사용처는 엣지 패널이라 설정 화면 방문이 드물 수 있다. 광고 가능한 지면의 실제 사용량이 적다면 설치 수가 늘어도 수익이 작을 수 있다. 수익 추정은 `실제 광고 노출 수 ÷ 1,000 × 실제 eCPM`에서 시작하되 국가·광고 형식·동의·충족률·무효 트래픽 등을 반영한다. 고정 월수익을 약속하지 않는다.

### 단계 C — 작은 광고 실험

**위치 원칙:** 사용자 스스로 연 일반 설정/테마 화면 안에서만 광고 영역을 검토한다. 엣지 핸들·라이팅·알림 패널·잠금 화면·다른 앱 위·서비스 알림에는 광고를 넣지 않는다. 패널을 열거나 답장할 때 전면 광고를 끼워 넣지 않는다. Play는 앱 밖 광고와 시스템 알림을 흉내 내는 광고, 종료/홈 동작을 방해하는 광고 등을 제한한다. [광고 정책](https://support.google.com/googleplay/android-developer/answer/9857753?hl=en)

**데이터 원칙:** 알림 제목·본문·발신자·방 이름·답장·발견 앱·차단어를 광고 타기팅, SDK 속성, 분석 이벤트, 로그에 넣지 않는다. 이는 Slivue가 채택할 강한 제품 원칙이다. 민감 권한의 목적 외 사용 제한과 설치 앱 목록 등의 광고 활용 제한도 별도로 준수한다. [민감 권한·API 정책](https://support.google.com/googleplay/android-developer/answer/16558241?hl=en)

광고 영역 한 곳·제한된 빈도부터 시작하고, 이탈·불만·배터리·성능·무효 트래픽이 악화되면 중단한다. 알림 내용과 광고 로직의 접근 경계를 설계하고 테스트한다.

## 7. 결정 기록

| 결정 | 이번 권고/상태 |
| --- | --- |
| 첫 출시 광고 | 없음 권고. SDK 추가하지 않음 |
| GitHub 공개 여부 | 공개 유지 권고. 실제 설정 변경 없음 |
| 기존 패키지 유지 | 우선 확인할 방향. Console·교차 설치 검증 전 보장하지 않음 |
| 앱 서명키/업로드 키 | 역할 분리. 실제 새 키 생성·등록은 아직 하지 않음 |
| 직접 APK 배포 유지 | 기존 사용자 보호를 위해 즉시 중단하지 않음. Play와의 채널 전략 확정 필요 |
| 유료 기능 | Play 첫 출시·안정 운영 이후 재검토 |
| 소유자에게 필요한 답 | 계정 유형·생성일·국가, 공개 연락처, 기존 사용자 유지 조건 |

본 문서의 권고를 승인했다고 해서 계정 결제·법적 약관·앱 서명키 이전·패키지 변경·프로덕션 게시가 자동으로 완료되는 것은 아니다. 각 실행 단계에서 소유자 확인이 필요한 항목을 구분한다.
