# Slivue Google Play 준비 구현·검증 결과

기준일: **2026-10-31**, 소스 버전: **v1.3.27 / 157**.

## 결론

Play 전용 빌드와 알림 처리 동의·중지·철회 기능을 구현하고 로컬 검증을 통과했다. **Play 앱 등록·게시 또는 최종 제출 준비 완료를 의미하지 않는다.** 공개 운영 이름·이메일·정책 URL·시행일·별도 업로드 키가 아직 없다. 정책은 두 언어 모두 초안이고 현재 AAB는 미서명 기술 후보다.

| 구분 | 설치 식별자 | 배포·호환성 |
| --- | --- | --- |
| Play판 | `com.devdooly.slivue` | 새 앱. Play 앱 서명·업로드 키와 설치 검증을 별도로 진행 |
| 기존 GitHub판 | `com.devdooly.notificationedge` | 기존 설정과 서명 계보 유지. 기존 공개 APK의 업데이트 경로 유지 |

두 앱은 동시에 설치할 수 있지만 설정·권한·알림 이력을 자동으로 옮기지 않는다. Kotlin namespace, 데이터 키, 외부 명령 식별자는 이번 이름 변경 대상이 아니다.

## 구현 내용

- `direct`와 `play` 소스 세트를 나눴다. Play 산출물에서 자체 APK 업데이터, 설치 권한, FileProvider, 인터넷 권한, 온라인 폰트 제공자, 진단 원문 내보내기를 제외했다. 시스템·사용자 폰트는 유지했다.
- compile/target SDK 36, 최소 API 26, AGP 8.13.2·Kotlin 2.3.10·Gradle 8.14·JDK 17을 사용한다.
- Play의 구형 백업·클라우드·기기 간 전송 규칙에서 모든 저장 도메인을 제외한다. 실제 제조사 이전 결과를 정적 설정만으로 보장하지는 않는다.
- 설치별 비백업 영역에 고지 동의 버전·시각·중지 상태를 원자 교체 저장한다. 동의와 실제 OS 권한은 별개로 검사한다. 거절·나중에·화면 닫기를 동의로 기록하지 않는다.
- 중지·철회와 알림 저장·답장 전달·미디어 제어·발견 앱 기록을 동일한 접근 세대 검사로 묶었다. 메모리 이력을 비우되 다른 앱의 원본 알림은 지우지 않는다.
- Application이 정확한 알림 접근 설정 URI를 관찰한다. 시스템 권한을 철회하면 설정 화면에 돌아오지 않아도 동의·메모리·서비스 중단 경로가 실행된다. 리스너 종료 시에도 재검사한다.
- 실행 상태 알림에 중지 액션을 추가하고 LOW 중요도의 새 채널을 사용한다. 알림 보내기 권한은 다른 앱 알림 읽기와 구분한 선택 항목이다.
- 같은 이름의 두 앱을 함께 설치한 경우 API 30 이상은 해당 설치 식별자의 알림 접근 상세 화면을 우선 연다. 구형·미지원 OS에서는 전체 목록으로 대체한다.
- 한·영 로컬 개인정보 안내와 Play 전용 정책 초안을 제공한다. 로컬 정책 화면은 JavaScript·네트워크·파일/콘텐츠 접근을 차단한다. 직접 배포판에는 실제 배포 동작에 맞는 별도 로컬 안내를 둔다.
- 한·영 등록정보 미리보기와 1024×500 불투명 RGB 기능 그래픽을 준비했다. 최종 스토어 스크린샷·심사 시연 영상은 별도다.

## 실제 검증 결과

| 추가 빌드 | 성공 | Play AAB, 직접 배포 축소 APK, 두 배포판 계측 APK |

| 직접 배포 서명 | 일반·축소 APK 통과 | Android 8 기존 인증서와 신형 OS 회전 인증서, v2/v3 검증 |
| 네이티브 정렬 | 정적 검사 통과 | AAB의 64비트 ELF 4개 PT_LOAD 모두 16KB 이상, 직접 배포·Play 후보 APK ZIP 16KB 정렬 통과 |
| 최종 제출 게이트 | 의도한 실패 확인 | 미확정 정보·초안·업로드 키 부재로 후보 확정 차단 |

Android 8은 `cmd notification`을 구현하지 않는다. 테스트 전용 헬퍼는 그 버전에서만 기존 Secure 설정의 다른 리스너 항목을 보존하고 해당 테스트 컴포넌트만 변경한다. 원래 자신의 권한 상태를 복원하며 미지원 검증을 건너뛰지 않는다. 배포 앱에는 이 권한 변경 도구가 포함되지 않는다.

수동 UI에서는 고지 거절 후 미저장, 명시적 동의 저장, 중지 후 프로세스 재시작 시 중지 유지, 사용자 재개, 로컬 정책의 한국어·영어 전환을 확인했다. API 36 화면·UI 계층 증거는 로컬 `app/build/play-verification-v1.3.27/`에 있으며 빌드 산출물이므로 Git에는 넣지 않는다. 개인정보 또는 실제 사용자 대화는 시험 알림으로 사용하지 않았다.

### 로컬 Play 기술 후보

- 경로: `app/build/outputs/bundle/playRelease/app-play-release.aab`
- 패키지·버전: `com.devdooly.slivue`, `1.3.27 (157)`, 최소 26 / 대상 36
- 크기: **11,116,426 바이트**
- SHA-256: `4fc930fa2c241365f4870b2b552fde1d1058a50a73d4f063cd5a5555ff4a20df`
- 서명: **없음**, 정책: **한국어·영어 모두 draft**
- 검사한 실제 manifest: 설치·인터넷 권한 및 FileProvider 없음, `allowBackup=false`, 구형/cloud/D2D 각각 9개 도메인 전체 제외.

이 해시는 이 PC에서 생성한 기술 후보만 식별한다. 다른 OS·CI에서 재빌드한 파일과 같다고 가정하지 않는다. **이 파일을 Play 업로드 완성본으로 사용하지 않는다.**

### 제출 차단도 실제로 시험한 항목

1. `preparePlaySubmission`: 운영 이름·이메일·HTTPS 정책 URL·정책 승인·한영 확정본·업로드 서명 미완료로 실패한다.
2. 업로드 키 4개 중 일부만 설정한 일반 `bundlePlayRelease`도 즉시 실패한다.
3. 키 4개를 설정하면 하위 `packagePlayRelease`와 `signPlayReleaseBundle`에도 준비 검사가 필수로 선행한다. 실제 Gradle 그래프에서 확인했다.
4. 기존 직접 배포 키를 임시로 업로드 설정에 지정한 실행은 재사용 금지·초안 조건으로 실패했다. Play 키를 새로 생성하거나 등록한 것이 아니며 기존 미서명 후보 해시도 변하지 않았다.
5. 성공하지 않은 이번 시도는 `app/build/play-submission/latest-attempt.json`에 `not_ready`로 남는다. 과거 성공 파일을 이번 결과로 사용하지 않는다.

실제 별도 업로드 키가 없으므로 최종 서명 AAB 성공 경로·Play App Signing 설치물·다음 Play 버전 업데이트는 아직 시험하지 않았다. 서명 파일 존재 검사와 암호학적 유효성 검사는 구분하며, 최종 준비 태스크는 모든 AAB 본문 항목을 읽어 지정 업로드 인증서와 서명을 검증하도록 구현했다.

## 남은 작업 순서

1. **소유자 확정:** 정당하게 등록 가능한 Play 계정, 공개 개발자 이름·문의 이메일, 배포 대상·연령 정보를 결정한다. 비밀번호·개인 주소·신분 서류를 Git이나 채팅에 올리지 않는다.
2. **정책 확정·게시:** 문의 수신 서비스와 HTTPS 호스팅을 정하고 실제 운영 내용·시행일을 한영 정책과 앱 자산에 동일하게 반영한다. 로그인 없이 읽히는 실제 URL을 확인한다. HTML 소스 보기 주소는 공개 정책 페이지를 대신하지 않는다.
3. **별도 서명 준비:** Play 업로드 키를 안전하게 생성·보관하고 Play 앱 서명키와 구분한다. 기존 GitHub 키를 재사용하지 않는다.
4. **최종 후보 생성:** 승인과 실제 메타데이터를 설정한 뒤 `preparePlaySubmission`을 통과시킨다. 성공 폴더의 AAB·검증 JSON·해시를 함께 보관한다.
5. **최종 행동 검증:** 실제 전송·로그·SDK, 폰트 가져오기/삭제, 백업·복원·OEM 이전, 삼성 실기기, 잠금·회전·분할 화면, 16KB 런타임을 확인한다. 이번 두 AVD의 실제 페이지 크기는 4KB이므로 16KB 실행 통과로 기록하지 않는다.
6. **Console 입력·내부 테스트:** 등록정보·최종 스크린샷·시연 영상·FGS 설명·Data safety·광고/접근/등급 답안을 최종 앱과 대조한다. Play가 서명한 설치와 다음 후보 업데이트, Pre-launch report를 확인한다.
7. **해당 계정의 테스트·게시:** 실제 요구되는 비공개 테스트와 프로덕션 액세스 신청을 진행한 뒤 소유자가 최종 제출·게시를 확인한다. 이번 에뮬레이터 시험은 실제 참여자 테스트를 대체하지 않는다.

세부 실행 명령과 미완료 점검 항목은 [제출 점검표](GOOGLE_PLAY_SUBMISSION_CHECKLIST.md)를 따른다. Data safety는 아직 최종 신고 답안이 아니다.

## 확인한 공식 근거

- 대상 SDK 요구는 [Google Play 대상 API 안내](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en)를 확인했다.
- 네이티브 정렬과 실제 실행의 구분은 [Android 16KB 페이지 지원 안내](https://developer.android.com/guide/practices/page-sizes)를 따른다.
- 고지·동의·공개 개인정보 안내는 [Google Play 사용자 데이터 정책](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en)을 기준으로 준비했다. 정책 준수·법률 검토·심사 승인을 코드 검증만으로 확정하지 않는다.
