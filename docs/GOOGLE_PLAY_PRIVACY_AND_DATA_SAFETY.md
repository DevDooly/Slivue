# Slivue 개인정보·권한·Data safety 준비서

## 1. 문서 상태

2026-09-05, v1.3.19(`4837ea2`) 기준 소스 감사와 **첫 무광고 Play 버전의 설계 초안**이다. 이 문서는 공개 개인정보처리방침 완성본이나 Play Console에 그대로 제출할 최종 답안이 아니다. 법적 운영 주체·연락처·배포 국가·최종 SDK·실제 네트워크와 백업 동작을 확인한 뒤 확정한다.

[전체 출시 계획](GOOGLE_PLAY_LAUNCH_PLAN.md) · [서명·수익화 전략](GOOGLE_PLAY_SIGNING_AND_MONETIZATION.md)

### 2026-10-31 구현 착수 업데이트

아래 본문은 **2026-09-05의 직접 배포판 감사·계획 기록**을 보존한 것이다. 새 Play판의 최종 상태를 뜻하지 않는다. 사용자는 아직 Play 앱을 등록하지 않았고, 새 Play 패키지를 **`com.devdooly.slivue`**로 선택했다. 기존 GitHub판 `com.devdooly.notificationedge`는 업데이트 호환성을 위해 유지한다. 두 앱의 설정·권한·이력은 자동 이전되지 않는다.

새 Play판은 별도 AAB, 자체 APK 설치·업데이트/Google Fonts 제공자/알림 원문 진단 내보내기 제외, 백업·D2D 제외 규칙, 비백업 동의 기록, 명시 고지·권한 확인·전체 중지 흐름을 준비하고 있다. 구현 완료와 최종 산출물·통신·실기기 검증은 각각 증거로 확인해야 한다.

공개 개발자명·문의 이메일은 사용자 답변상 **미정**이다. [한국어 정책 HTML 초안](privacy/ko.html)·[영어 정책 HTML 초안](privacy/en.html)과 앱 내부용 동일 전문은 **Google Play판 전용 준비본**이며, 최종 시행 중인 공개 정책이 아니다. 운영 정보·공개 URL·시행일 확정과 최종 구현 검토 전에는 그대로 제출하지 않는다. 직접 배포판의 기존 Google Fonts·GitHub 통신·백업 동작에 이 Play 전용 초안을 무조건 적용하지 않는다.

남은 순서, Data safety 잠정 답과 확정 증거, 권한/중지 검증, FGS 신고·시연, 소유자의 실제 Console 작업은 [제출 준비·심사 점검표](GOOGLE_PLAY_SUBMISSION_CHECKLIST.md)에서 관리한다. 현재 **“데이터 수집 없음” 최종 신고는 확정하지 않았다.**

앱 프로세스가 종료되면 메모리 이력은 사라지지만, 리스너가 다시 연결되면 OS에 남아 있는 활성 알림을 다시 읽을 수 있다. 따라서 “앱을 닫으면 모든 관련 정보가 영구 삭제된다”는 표현도 사용하지 않는다.

## 3. 알림 접근 전 고지·동의

현재 권한 카드의 한 줄 설명과 시스템 권한 창만으로는 충분한 고지·동의를 보장하기 어렵다. 특히 다른 앱의 민감 내용을 백그라운드에서 읽는 사용 방식은 앱 안에서 명확히 설명한다. 개인정보처리방침 링크만 제공하고 곧바로 권한 설정을 여는 방식으로 대체하지 않는다. [User Data 정책](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en), [고지·동의 안내](https://support.google.com/googleplay/android-developer/answer/11150561?hl=en)

### 권고 흐름

1. 첫 설정 화면에서 권한별 목적과 미허용 시 제한을 표시한다.
2. 알림 접근 버튼을 누르면 아래 고지를 보여준다.
3. **동의하고 설정 열기 / 나중에**를 분리한다. 미리 선택된 동의나 다른 약관에 묶인 동의를 사용하지 않는다.
4. 동의 후 시스템 알림 접근 설정으로 이동한다. 복귀 시 실제 권한을 다시 확인한다.
5. 동의가 없거나 철회되면 리스너의 데이터 처리도 멈추도록 한다. 시스템 권한만 남은 예전 설치·백업 복원 경로도 시험한다.
6. 동의 버전·시각 정도만 기기에 저장한다. 복원한 동의로 새 기기에서 자동 민감정보 접근을 시작하지 않는다.

### 화면 문구 초안 — 구현 후 대조 필수

> **알림 접근을 사용하는 이유**
>
> Slivue는 화면 가장자리에서 알림을 모아 보여주기 위해 다른 앱이 보내는 알림의 제목, 내용, 발신자, 앱 이름과 수신 시각을 읽습니다. 설정 화면을 닫은 동안에도 알림 접근이 켜져 있으면 동작합니다.
>
> 이 정보는 알림 표시·필터링·빠른 답장에 사용합니다. 답장을 보내면 원래 메시지 앱에 전달됩니다. 첫 Play 버전에서는 알림 내용을 개발자 서버로 전송하거나 광고에 사용하지 않도록 설계합니다.
>
> 알림 이력은 기기 메모리에, 필터와 발견 앱 목록은 기기 저장소에 보관합니다. 시스템 알림을 지우는 것과 Slivue 이력을 지우는 것은 다를 수 있습니다. 언제든 설정에서 처리를 중지하고 이력을 지우거나 시스템 알림 접근 권한을 해제할 수 있습니다.

위 초안의 “전송하지 않음”, 중지·삭제 경로, 백업 설명은 **최종 Play 구현과 검사 결과가 일치할 때만 제품 문구로 확정**한다. 계획 문구 자체를 검증 완료 증거로 쓰지 않는다.

### 다른 권한과 구분

| 항목 | 설명·제어 원칙 |
| --- | --- |
| 알림 접근 | 다른 앱의 알림을 읽음. 별도 민감정보 설명과 동의 |
| 다른 앱 위에 표시 | 핸들·라이팅 표시. 시스템 권한·결제 화면을 가리거나 조작하지 않음 |
| 알림 보내기 | Slivue 실행 상태를 알리는 권한. 다른 앱 알림을 읽는 권한과 다름 |
| 배터리 예외 | 선택. 거부해도 강제 종료/반복 유도하지 않고 제조사 제한 설명 |
| 외부 제어 | 현재 기본 거부 유지. 사용자가 활성화한 명령만 허용 |

현재 없는 접근성 서비스·SMS/통화기록·전체 설치 앱 조회·전체 화면 인텐트 권한을 심사 우회나 불필요한 기능 때문에 추가하지 않는다.

## 4. FGS·잠금·중지 UX

`specialUse`는 무제한 승인용 유형이 아니다. Play에는 기능, 왜 지연/중단할 수 없는지, 시작·작동 영상 등 실제 요구 자료를 제출하고, manifest의 사용 설명도 구체화한다. 사용자가 시작한 핸들·라이팅이라는 앱 목적을 설명하되 승인 가능성을 보장하지 않는다. [FGS 신고](https://support.google.com/googleplay/android-developer/answer/13392821?hl=en), [specialUse 유형](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use)

확인한 개선 대상:

- FGS 알림은 현재 `IMPORTANCE_MIN`/`PRIORITY_MIN`이다. 공식 시작 지침의 LOW 이상 요구에 맞춰 가시성을 점검한다. 기존 채널은 코드 값 변경만으로 중요도가 갱신되지 않을 수 있으므로 설치/업데이트 경로를 시험한다. [FGS 시작 지침](https://developer.android.com/develop/background-work/services/fgs/launch)
- 핸들과 라이팅이 모두 꺼져야 서비스가 종료된다. 사용자가 이해하기 쉬운 **전체 중지**와 알림의 중지 동작을 제공하는 방향을 권고한다.
- `POST_NOTIFICATIONS` 런타임 요청 경로를 보완한다. 미허용이 모든 FGS 실행을 무조건 금지하는 것으로 설명하지 않고 실제 OS 동작과 안내를 일치시킨다.
- 권한 철회 시 기존 메모리 알림이 계속 보이는지, 잠금 상태에서 패널·외부 명령으로 민감 내용이 노출되는지 실기기 확인한다. 현재 실제 노출 사고가 확인된 것은 아니다.
- 사용자 강제 중지·OS 제한을 무시한 재시작이나 배터리 보호 우회는 구현하지 않는다.

## 5. 진단·백업·삭제 정리

### 진단은 익명 데이터가 아니다

[NotificationDumpSanitizer](../app/src/main/java/com/devdooly/notificationedge/util/NotificationDumpSanitizer.kt)는 일부 비밀 키 이름·메일·전화번호·숫자 등을 마스킹하지만 임의의 문장과 사람 이름을 모두 제거하지 않는다. 전체 복사에서는 제목을 덤프 외부에 붙이는 경로도 있다. 민감 클립보드 표시는 미리보기를 보호할 뿐 익명화가 아니다.

권고는 첫 Play 버전에서 원문 덤프와 전체 복사를 제외하고 구조·오류 유형·건수 위주의 지원 자료만 남기는 것이다. 유지할 경우에는 개인정보가 남을 수 있다는 경고, 공유 전 미리보기, 최소 항목 선택, 본문/제목 제거 테스트가 필요하다. 공개 GitHub 이슈·Slack에 진짜 대화나 인증코드를 보내도록 안내하지 않는다.

### 백업 정책은 별도로 결정

[기존 백업 규칙](../app/src/main/res/xml/backup_rules.xml)과 [Android 12+ 규칙](../app/src/main/res/xml/data_extraction_rules.xml)은 SharedPreferences 및 설정 DataStore를 클라우드 백업 대상으로 둔다. 이 파일에 발견 앱·필터 키워드도 들어 있다. Android 12+ 파일에는 `device-transfer`가 없으므로 D2D 범위를 명시적으로 제한했다고 볼 수 없다. [Android 자동 백업](https://developer.android.com/identity/data/autobackup)

권고 분리:

- UI 색상·크기 등 비민감 설정: 필요한 경우 백업 허용.
- 발견 앱·차단어·동의·진단 상태: 별도 저장 영역과 명시적인 백업 제외/재확인 정책.
- 사용자 폰트: 클라우드·기기 간 이동 각각 허용 여부 결정.
- 알림 원문: 디스크/클라우드에 새로 저장하지 않는 첫 버전 방향 유지.

`allowBackup=false` 한 줄로 모든 제조사·기기 간 이전이 완전히 차단됐다고 단정하지 않는다. 최종 cloud/D2D 규칙과 실제 복원 결과를 확인한다.

### 제공해야 할 삭제·철회 안내

- 앱 내 이력 지우기와 OS 알림 삭제의 차이
- 발견 앱 목록·차단어·사용자 폰트 삭제
- 전체 처리 중지 및 알림 접근 권한 철회
- 앱 데이터 삭제/제거와 OS 백업 복원에 대한 설명

계정 생성 기능이 없으므로 가상의 회원탈퇴 기능을 만들 필요는 없다. 향후 앱 계정을 도입하면 별도로 계정 삭제 정책을 검토한다.

## 6. Data safety 작성 작업표

Google의 Data safety에서 **온디바이스 접근·처리**와 **기기 밖 수집**, **제3자 공유**는 같은 개념이 아니다. SDK 처리도 포함되며 사용자 지시로 다른 앱에 전달하는 경우의 예외는 조건을 확인해야 한다. 따라서 민감 권한을 쓴다고 자동으로 모든 항목을 수집으로 체크하지도, 자체 서버가 없다고 자동으로 수집 없음으로 체크하지도 않는다. [공식 정의와 신고 방법](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en)

| 검토 항목 | 현재 잠정 판단 | 최종 답변에 필요한 증거 |
| --- | --- | --- |
| 알림 원문·발신자 | 소스상 기기 내 처리. 수집 없음 후보이나 미확정 | Play 최종 빌드의 네트워크·SDK·로그·진단 확인 |
| 빠른 답장·사용자 복사 | 사용자 요청에 따른 다른 앱 전달 | 공유 예외 조건·실제 UI·처리방침 대조 |
| 발견 앱·차단어 | 로컬 저장·설정 백업 포함 | 최종 백업 범위·직접 전송 여부 |
| IP 등 접속 정보 | GitHub/폰트 제공자 등 기능별 별도 검토 | 유지된 외부 통신과 제공자 문서·실측 |
| 오류·사용량·식별자 | 현재 별도 분석 SDK 없음 | 전이 SDK 및 최종 산출물 검사 |
| 향후 광고 | 새 수집/공유 발생 가능성이 큼 | 실제 SDK 버전·동의 흐름·지역별 설정 재감사 |

최종 신고 절차:

1. 제출할 Play 산출물·SDK 버전·국가별 기능을 고정한다.
2. 최초 실행/미동의/동의/철회/폰트/지원 기능/백그라운드의 통신을 확인한다.
3. 데이터 항목·목적·선택/필수·임시 처리·공유 예외를 증거와 함께 기록한다.
4. 여러 활성 Play 버전·지역에서 다르게 처리한다면 이를 누락하지 않는다.
5. 처리방침·스토어·App content와 교차 검수한 뒤 소유자가 제출한다.
6. 광고/분석/계정 기능 추가 전에 재신고가 필요한 변경을 반영한다.

검사를 위해 사용자 기기의 보호를 해제하거나 인증서 고정을 우회하지 않는다. 테스트 빌드·합성 알림·허용된 네트워크 진단 환경을 사용한다.

## 7. 개인정보처리방침 작성 골격

다음 항목의 미정 값을 채우고, 최종 앱과 일치하는 문장으로 별도 공개 페이지를 만든다. Play에는 로그인·지역 제한 없는 공개 URL과 앱 내부 링크 또는 전문이 필요하며 PDF로 대체하지 않는다. 일반 사용자가 정책 내용을 편집할 수 없게 관리한다. 이 프로젝트는 앱 내부 링크 제공을 우선 권고한다. [개인정보처리방침 요구](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en)

| 항목 | 작성할 내용 |
| --- | --- |
| 운영 주체 | `[확정할 법적 이름/개발자명]`, Slivue와의 관계 |
| 시행·개정일 | `[최종 시행일]`, 변경 통지 방법 |
| 문의 | `[실제 관리 이메일]`, 필요한 지역별 연락처 |
| 처리 정보 | 위 데이터 흐름에서 실제 유지된 항목만 기재 |
| 목적 | 알림 표시·필터·사용자 답장·설정 기능 등 |
| 처리 위치/제공 | 기기 내부, 원래 메시지 앱, 실제 사용하는 제공자·국외 처리 여부 |
| 보유/삭제 | 메모리 이력의 한계·활성 알림 재조회·로컬 설정·백업·사용자 삭제 |

| 아동/지역 | 실제 대상 연령·배포 국가에 맞는 요구 확인 |

원문 민감정보를 광고에 쓰지 않는 제품 원칙은 명확히 유지한다. 국가별 개인정보 법령 적합성은 운영 주체와 실제 사업 상황을 기준으로 별도 검토한다.
